### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Доступность сервисов должна составлять 99,9%. |
| 2 | При сбое основного ЦОД сервис подачи депозитных заявок должен быть восстановлен в резервном ЦОД с RTO не более 1 часа и RPO не более 15 минут. |
| 3 | Интернет-банк не должен напрямую работать с API или БД АБС в новом процессе. |

| 7 | При временной недоступности АБС заявка клиента не должна теряться, а сохраняться в DLQ с помощью паттерна outbox. |

| 9 | Новые компоненты должны быть совместимы с существующими технологиями банка. Например, MS SQL, Oracle, Java, Python, .NET. |

### <a name="_qmphm5d6rvi3"></a>**Решение**
Для MVP открытия депозитов онлайн предлагается добавить отдельный сервис депозитных заявок. Он будет принимать заявки с сайта и интернет-банка, хранить их состояние и передавать заявки на дальнейшую обработку в АБС и связанные системы.

Основная идея решения — не подключать сайт и интернет-банк напрямую к АБС. АБС уже испытывает нагрузку, а её база данных масштабируется только вертикально. Поэтому новый сервис депозитных заявок выступает промежуточным слоем между онлайн-каналами и АБС.

В рамках MVP автоматическое открытие депозита не реализуется. Заявка клиента передаётся на обработку сотруднику депозитного бэк-офиса, который подтверждает условия депозита в АБС. После подтверждения ставки и после открытия депозита клиент получает SMS-уведомления.

Для сайта сценарий отличается тем, что новый клиент не может полностью открыть депозит онлайн. Он оставляет заявку, после чего с ним связывается менеджер кол-центра. Далее клиент должен прийти в отделение для идентификации.

Для интернет-банка клиент уже авторизован. Он видит общие и персонализированные депозитные предложения, указывает счёт и сумму депозита, подтверждает операцию SMS-кодом и отправляет заявку.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Интегрировать сайт и интернет-банк напрямую с АБС.

Плюс: меньше новых компонентов.
Минусы: увеличивается нагрузка на АБС, сохраняется сильная связность онлайн-каналов с АБС, повышается риск отказа основной банковской системы. В задании указано, что БД АБС уже перегружена, поэтому вариант не выбран.

2. Реализовать весь новый функционал внутри существующего интернет-банка.

Плюс: меньше отдельных сервисов.
Минусы: интернет-банк является монолитом на платформе подрядчика, часть изменений потребует участия подрядчика. Также текущая архитектура интернет-банка не готова к требуемой доступности и масштабированию. Вариант не выбран как основной.

**Недостатки, ограничения, риски**

1. В MVP сохраняется ручная обработка заявки сотрудником депозитного бэк-офиса. Это не решает полностью проблему операционных издержек, но позволяет быстрее запустить онлайн-подачу заявок.

2. АБС остаётся ключевой системой для подтверждения условий и открытия депозита. При недоступности АБС заявка может быть принята, но её обработка будет отложена.
